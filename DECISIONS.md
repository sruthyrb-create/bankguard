# Design decisions

One line per decision, newest at the bottom.

- 2026-11-13 Hardware is an RTX 5050 Laptop GPU (8 GB VRAM, Blackwell sm_120) on WSL2, so the spec's 8 GB tier applies: QLoRA only, quantized local models.
- 2026-11-13 Local agent baseline is Qwen2.5-7B-Instruct-AWQ instead of 7B fp16 (about 15 GB, does not fit); fallback is Qwen2.5-3B-Instruct, whose licence is Qwen Research rather than Apache-2.0.
- 2026-11-13 The fp16 vs 4-bit comparison runs on Qwen2.5-1.5B, the only model that fits in fp16, so both precisions can be measured on the same model.
- 2026-11-13 The LLM judge must come from a different model family than the teacher, to avoid a model grading its own outputs.
- 2026-11-13 One OpenAI-compatible client (`openai` SDK) talks to both Groq and vLLM; only base_url and model change.
- 2026-11-13 Two conda envs: `bankguard` (app, eval, training) and `bankguard-vllm` (serving), because vLLM pins its own torch build.
- 2026-11-13 Core requirements are pinned now; GPU/ML packages are added and pinned in the phase that first needs them, to keep installs fast and failures isolated.
- 2026-11-13 A smoke test fails if real bank branding appears anywhere in the repo (rule 3).
- 2026-11-13 Llama 3.3 70B is no longer offered on Groq (checked 2026-11-13). Teacher and strongest baseline is now `openai/gpt-oss-120b` (Apache-2.0, so no licence naming rule for distilled models); judge is `qwen/qwen3.8-27b`.
- 2026-11-13 Known judge risk: the judge is Qwen-family like the local models, so it may favour them slightly; mitigated by rule-based grading wherever possible and by measuring judge agreement on hand-labelled items.
- 2026-11-13 Synthetic data uses a fixed end date (2026-10-31) and a single seeded RNG, so `bank.db` is byte-for-byte reproducible.
- 2026-11-13 Cards are stored as last 4 digits only; no full card number ever exists in the database.
- 2026-11-13 Anomaly labels (`is_anomaly`, `anomaly_type`) stay in the database for grading but tools never return them.
- 2026-11-13 Tools enforce authorization themselves (account_id must equal the session's account), not only the prompt; a prompt can be talked around, a code check cannot.
- 2026-11-13 Reg E timeline in `open_dispute` counts business days as weekdays and ignores federal holidays (simplification, stated in the tool output).
- 2026-11-13 `get_transactions` returns at most 50 rows (newest first) to keep tool output inside the model's context.
- 2026-11-13 The bank.db hash can differ between machines (SQLite writes its version into the file); determinism is tested on row contents, which match for the same seed.
- 2026-11-13 Reg E is fetched from the official eCFR API at a fixed snapshot date (2026-11-01), so chunk ids and citations are stable across rebuilds.
- 2026-11-13 Only Subpart A (1005.1-1005.20) is indexed; remittance-transfer rules (Subpart B) are out of scope for a card/account support agent and would add off-topic retrieval hits. Official interpretations (Supplement I) are left out for now.
- 2026-11-13 Chunks group paragraphs by top-level letter ((a), (b), ...) and split at 180 words, because all-MiniLM-L6-v2 truncates input at 256 tokens. Chunk ids look like `1005.11(c)#1`, readable enough to cite.
- 2026-11-13 FAISS IndexFlatIP on L2-normalised embeddings (exact cosine search); a few hundred chunks need no approximate index.
- 2026-11-13 PyTorch is installed from the CUDA 13.0 wheel index (needed for Blackwell sm_120) before the other ML packages; its exact version is pinned after the first install.
- 2026-11-13 PyTorch pinned to 2.14.1+cu130, the version verified with CUDA on the RTX 5050.
- 2026-11-13 Retries use the OpenAI SDK's built-in exponential backoff (max_retries=4) instead of custom retry code.
- 2026-11-13 LLM responses are cached on disk by a hash of the full request (model, messages, tools, temperature, seed), only at temperature 0; cached calls are marked `cached: true` in traces so latency metrics can exclude them.
- 2026-11-13 The account id is put in the system prompt and also enforced by the tools; the prompt helps the model, the code check is what actually protects data.
- 2026-11-13 Traces store result summaries (counts, chunk ids), not full transaction lists, to keep trace files small and free of bulk customer data.
- 2026-11-13 Agent and API tests use a scripted fake LLM, so the loop logic is tested offline and deterministically; real-model behaviour is measured by the eval harness instead.
- 2026-11-13 Phase 3 is split: 3a = agent, tracing and API on Groq; 3b = the same agent on a local vLLM server (separate env), so the Groq path is usable before the local setup.
- 2026-11-13 Fix from the first Groq demo: `open_dispute` wrongly used 45 days for point-of-sale debit transactions. It now applies all three 90-day cases in 12 CFR 1005.11(c)(3)(ii) (not initiated in a US state, point-of-sale debit, within 30 days of first deposit) and labels limits as calendar days.
- 2026-11-13 Accounts are now checking/savings with debit cards only. Regulation E covers debit/EFT accounts; credit-card disputes fall under Regulation Z, which this project does not model.
- 2026-11-13 Observed failure in the first demo: gpt-oss-120b turned Reg E's 45/90 calendar days into "business days" while citing the correct chunks. Added a prompt rule to quote day counts as written; the eval set will include a scenario for this, because a citation check alone does not catch it.
- 2026-11-13 The policy index (embedding model) is loaded before the first turn in the CLI and API, so the first policy question's latency does not include about 25 s of model loading.
- 2026-11-13 Groq validates tool calls against the JSON schema and returns HTTP 400 `tool_use_failed` when the model's call doesn't match. The agent now catches this, tells the model why, and retries within max_steps; each rejection is traced and counted as an invalid tool call (a metric, per spec risk 17).
- 2026-11-13 Added an optional `limit` (1-50) to `get_transactions`, because "show my last N transactions" is a natural request and the model reached for such a parameter.
- 2026-11-13 The demo's second turn names the transaction id. When the user only says "the duplicate charge" and both charges are identical, asking which one is the correct behaviour; that case becomes an eval scenario.
- 2026-11-13 Grounding checks must accept both [id] and 【id】 citation brackets; gpt-oss uses the latter.
- 2026-11-13 Root cause of the API 400 (from the trace): gpt-oss-120b sent `null` for every unset optional parameter, and the schemas only allowed string/number. All optional parameters now accept null, and a test enforces it for every tool.
- 2026-11-13 Guardrails run in a fixed order: PII masking, then the injection classifier, then the topic filter (input); schema check and action policy before each tool call; grounding check and PII-leak redaction on the final answer.
- 2026-11-13 The model, traces and history only ever see the masked user message ([SSN], [CARD], [PHONE], [EMAIL]). Any 13-19 digit run is masked as a card, Luhn-valid or not: no legitimate number that long exists in this domain, and a mistyped card number is still sensitive.
- 2026-11-13 A message blocked at input is refused without an LLM call, and the history keeps a placeholder instead of the blocked text, so a later turn cannot build on the attack.
- 2026-11-13 Injection classifier is protectai/deberta-v3-base-prompt-injection-v2. Its threshold is chosen on a 64-message dev set by a rule fixed in advance: highest injection recall with at most 5% of benign dev messages blocked, ties to the higher threshold. Dev numbers are optimistic (tuned and measured on the same set); the held-out number comes from the Phase 6 red-team set, and a test checks that no dev message reappears in scenario files.
- 2026-11-13 Known limit: the classifier truncates at 512 tokens, so an injection placed after that is not scored. It also runs on user messages only, not on tool output; indirect injection (e.g. via transaction memos) is left to the system prompt rule and is a Phase 6 red-team category.
- 2026-11-13 The topic filter is rule-based and looks for intent ("should I buy", "invest in", "stock tips", another account id, "someone else's account"), not topic words, so questions like "is a stock purchase on my debit card covered by Reg E?" pass. The dev set has hard negatives of this kind, and a test requires zero topic-filter false refusals on them.
- 2026-11-13 Action policy for open_dispute: the latest user message must be affirmative and not decline or postpone the action, and the transaction id must appear in that message or be the only transaction id in the assistant's preceding question. Denied calls are not executed; the model gets an error telling it to ask for confirmation by id.
- 2026-11-13 Grounding check: every cited id ([id] or 【id】) must have been returned by search_policy in the same turn; a citation without the #n suffix counts if that paragraph was retrieved. On failure the model gets one repair attempt (max_repairs: 1) with the list of retrieved ids, then a fixed fallback answer. Answers without citations are not blocked here; whether a policy answer needed citations is graded in Phase 5.
- 2026-11-13 PII leaks in answers are redacted rather than regenerated (deterministic, no extra LLM call). Account ids other than the session's own are redacted too.
- 2026-11-13 The schema check validates tool arguments in code (types, required, extra keys, ranges, ACC-/TXN- id formats) instead of adding patterns to the schemas sent to Groq, which rejects some JSON-schema keywords.
- 2026-11-13 Fix: the injection threshold is picked from midpoints between neighbouring dev scores, compared unrounded. The first run rounded scores to 4 decimals, chose 1.0, and the classifier then blocked 0/20 dev injections (it only looked fine because the topic filter caught 2).
- 2026-11-13 The injection classifier scores the original user message, not the PII-masked one. It is a local model, so PII never leaves the machine, and masking raised benign scores on the dev set (dev-ben-11: 0.982 raw vs 0.999 masked; dev-ben-12: 0.012 vs 0.092). Raw scoring does not fully fix it: the SSN+email probe still scores about 0.99 unmasked. Everything sent to the LLM, traces and history stays masked.
- 2026-11-13 New guardrail `day_count_check`, added because gpt-oss stated "45 business days" and "90 business days" in two Groq runs while citing the correct chunk, which says "45 days" / "90 days" (calendar days). A business- or calendar-qualified day count in the answer must appear in this turn's tool output; Regulation E's unqualified "N days" count as calendar days. Unqualified counts in the answer are not checked. It shares the one repair attempt with the grounding check.
- 2026-11-13 Dev result for the injection classifier (results/guardrails_dev.json): threshold 0.99999934, injection recall 15/20, benign false refusals 1/28. Injections score 0.995-1.0, but benign messages that correct an earlier request ("Override my earlier request...", "New instructions from my side...", "Translate your last answer...") score up to 0.999999. The classifier reacts to instruction-like wording, not to intent, so it only works at the extreme top of its range. It stays on as one layer: the 5 dev misses ask for things other layers already stop (disputes without confirmation -> action policy; anomaly labels -> never returned by tools; "bypass rules" role-play -> system prompt). Phase 6 measures it on held-out attacks.
- 2026-11-13 Grounding and day-count checks now accept chunk ids and tool output seen anywhere in the conversation, not only in the current turn (a change from the original Phase 4 plan). In the Groq demo, turn 3 re-cited 1005.11(c)#1 and #3 retrieved in turn 2; the model did not search again when asked to repair, and a correct answer was replaced by the fallback. The retrieved text is still in the model's context, so citing it is grounded. Ids never returned by search_policy are still blocked.
- 2026-11-13 Cache hits now report their own (near-zero) latency; they used to replay the latency recorded when the response was cached, which made a 15 s cached call appear in traces. llm_call events also record Groq's server time (usage.total_time) and SDK retries, so slow calls can be split into server time vs queueing/rate-limit waits.
- 2026-11-13 Fix: day_count_check converts spelled-out numbers to digits before comparing (Regulation E writes "three business days", "two business days", "Sixty days"; gpt-oss writes "3 business days"). Without this, a correct answer was replaced by the fallback in the Groq demo.
- 2026-11-13 Groq free-tier rate limiting is real and now visible: a repair call took 11.8 s wall time with 1.3 s server time and retries=1, so about 10 s was a 429 back-off. The Phase 5 eval runner must pace requests and report latency without retry waits.
- 2026-11-16 Phase 5 stays on Groq's free tier (no paid tier until there is a reason). Pacing keeps each model under 8K counted tokens per minute and 30 requests per minute, and a per-day ledger stops a run at 170K counted tokens (below the 200K daily limit, leaving room for demos); runs resume from saved records. Counted tokens = prompt tokens minus provider-cached ones plus completion tokens, because Groq documents that cached tokens do not count toward rate limits (gpt-oss-120b supports prompt caching; the qwen judge does not). Pilot correction: provider caching saved little (2,304 of ~21K prompt tokens in 10 scenarios, all 768-token prefix hits). The budget works because eval scenarios average ~2.2K counted tokens, so 60 scenarios (~130K) fit in one day.
- 2026-11-16 Guardrails on vs off is cheap to compare: requests are identical until a guardrail intervenes, so the off run reuses the local response cache for most calls.
- 2026-11-16 The 60 eval scenarios are generated from bank.db by a script (ids, amounts and dates are read from the database, not typed by hand), and each stores the facts it relies on; a test fails if bank.db no longer matches. Policy scenarios only expect day counts and amounts that appear in the Regulation E text.
- 2026-11-16 Grading is rules first: database effects (exact disputes, required/allowed flags), required tools, no cross-account tool calls, no transaction or account ids that are neither the customer's nor mentioned by the customer, day counts consistent with the regulation, required strings, citations retrieved and on the right section, clarifying question when two charges are identical. Each scenario runs on a fresh copy of bank.db.
- 2026-11-16 The LLM judge (qwen3.8-27b, a different family from the agent) answers only what rules can't: is the final reply correct against the scenario's reference, and is it a refusal. It never sees the rule results. The hand-labelling sheet asks the same two questions without showing the judge's verdict; agreement is reported as raw agreement and Cohen's kappa.
- 2026-11-16 Success = all rule checks pass and the judge says correct and not a refusal. For refusal scenarios: a guardrail blocked the message or the judge says the model refused. False refusal = a benign scenario where any turn was blocked, any answer was a guardrail or max-steps fallback, or the judge says the final reply refused, so false refusals caused by output guardrails are counted, not only input blocks.
- 2026-11-16 Latency in the eval report is the LLM API time of turns whose calls all went to the API with no retries. Turn wall time includes pacing waits and local cache hits, so it is not reported as latency.
- 2026-11-16 Known limit of rule checks: they match strings (dates and amounts are normalised and listed in several formats), so a correct answer written unusually can fail a rule. Every rule failure is listed in the report and is reviewed before any number is used.
- 2026-11-16 Fix found by the pilot (eval-policy-11): the day-count guardrail counted the model's own search query as a source. The model searched for "Regulation E investigation 45 business days", the echoed query contained "45 business days", and its wrong answer passed. Sources are now only retrieved chunk text for search_policy and, for other tools, the result without strings the model sent as arguments. This is a general bug fix in the guardrail, not tuning of agent behaviour, but it was found on an eval scenario, so it is recorded here.
- 2026-11-16 No agent changes before the baseline. The pilot showed the agent asking for a "reason" instead of acting (3/10 scenarios: it asked before opening a confirmed dispute and before flagging an id it never looked up). Changing the prompt or tool schemas now would tune the agent on the test set. The full 60-scenario run is the baseline (v1); agent changes come after it as v2, reported side by side.
- 2026-11-16 Guardrail repair messages and fallbacks now store the rejected answer, and the report splits "no useful answer" outcomes into input blocks, output fallbacks (with whether the rejected answer was actually wrong) and model refusals. In the pilot, the one fallback (eval-policy-01) prevented a wrong "45 business days" answer: the guardrail was right, the repair failed because the model repeated the error.
- 2026-11-17 Run 0 (26 of 60 scenarios, guardrails on, before this change) is kept as evidence, renamed results/eval/runs/run0_gpt-oss-120b_on. In it, 3 of 26 scenarios failed with HTTP 413: on Groq's free tier a single request cannot exceed 8,000 tokens, and the agent re-fetched 50-row transaction lists while searching for one charge (up to ~10.5K tokens in one request). That is a platform limit, not answer quality, so the agent was made to fit before measuring the baseline ("Option A"), instead of excluding the failures afterwards.
- 2026-11-17 Agent v1 (the baseline) = run 0's agent plus three changes, with no prompt or tool-behaviour changes: (1) transactions reach the model as a column header plus one array per row (same fields, timestamps without seconds; a 50-row result goes from ~10.3K to ~5.5K characters); (2) a context guard estimates each request (characters / 3, deliberately high) and above 6,000 replaces older tool results with stubs that keep counts and ids, oldest first, then cuts rows from the newest list with a note to narrow the filters; session history keeps the full results; (3) dash variants are normalised before matching ids. Each run name carries the agent version (<model>_<on|off>_<version>), so v1 and later versions never mix.
- 2026-11-17 The pacer now waits until the last minute's counted tokens plus the estimated size of the next request fit under 8,000, instead of a fixed reserve.
- 2026-11-17 Fix: gpt-oss writes ids with a non-breaking hyphen (U+2011, "TXN‑040737"). Regexes for TXN-/ACC- ids missed them, so in run 0 the action policy blocked a confirmed dispute (eval-dispute-04), and the leak check would not have redacted another customer's account id written that way. All id, phone and date matching (input masking, topic filter, action policy, leak redaction, eval grader) now normalises dash variants to "-" first.
